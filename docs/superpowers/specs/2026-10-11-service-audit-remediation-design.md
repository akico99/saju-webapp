# 서비스 전반 점검 후속 조치 설계

작성일 2026-10-11 · 상태 사용자 승인됨 · 구현 진행

## 1. 목적

서비스 점검에서 확인한 결제 승인 후 중단 복구, 결제 취소 실패 기록, 민감한 URL의 분석 도구 전송, 관리자 화면의 저장형 XSS, 개인정보 보존 불일치, 백업 평문 전송, 운영 설정과 취약 패키지 문제를 바로잡는다. 고객은 결제 결과와 리포트를 잃지 않고 계정·개인정보를 관리할 수 있어야 하며, 운영자는 승인·취소·복구가 필요한 주문을 놓치지 않아야 한다.

현재 npm audit은 운영 의존성에서 취약점 17건(치명 1, 높음 11, 보통 5)을 보고했다. 카드사 2곳 심사가 진행 중이므로 심사자가 보는 상품, 가격, 결제 화면, 환불 정책, 사업자 정보와 결제 승인 요청 규격을 유지한다.

## 2. 목표와 제약

- 토스 승인 여부가 불명확해도 결제 원장과 고객 안내가 실제 상태와 어긋나지 않는다.
- 같은 결제의 재시도나 재시작 복구가 중복 크레딧·중복 주문을 만들지 않는다.
- 비밀번호 재설정 토큰과 결제 키를 분석 도구·리퍼러에 노출하지 않는다.
- 관리자 화면은 회원·주문 데이터가 HTML로 해석되지 않게 렌더링한다.
- 계정 탈퇴 시 서비스 제공용 개인정보와 결과물을 지우고, 보존이 필요한 거래 기록은 최소 정보로 분리한다.
- 운영에서 세션 키, 백업 암호화 키, 결과물 영구 저장 경로가 빠진 상태를 조기에 드러낸다.
- 카드사 승인 전후로 구매 상품, 금액, 결제 위젯 및 success/fail URL을 바꾸지 않는다. 코드 작업은 배포 전 검증 가능한 변경으로 준비한다.

## 3. 설계

### A. 결제 원장과 복구

카드 결제 행에 명시적인 승인·상품 시작 상태를 두고, 모든 상태 변경은 이전 상태를 조건으로 원자적으로 수행한다. 결제 승인 API 응답이 네트워크 오류로 유실되면 orderId 조회 API로 토스의 결제 상태, orderId, 금액, paymentKey를 대조한다. 일치하는 DONE 결제만 승인 완료로 기록한다. 조회 결과가 없거나 불확실하면 실패로 단정하거나 크레딧을 지급하지 않고 재조정 대기 상태에 남긴다.

승인 완료 기록과 포인트 원장 반영은 한 SQLite 트랜잭션에서 한 번만 일어나게 한다. 결제는 됐지만 job_id가 아직 없는 행은 재시도와 서버 시작 시 기존 활성 주문을 찾아 연결하고, 없으면 동일 결제 행의 저장 폼을 이용해 한 번만 시작한다. 활성 주문 고유 제약과 결제 행 선점으로 동시 요청을 막는다. job_id가 기록되기 전에는 복구에 필요한 입력을 지우지 않는다.

상품 시작 실패 시 먼저 취소 중 상태를 원자적으로 선점하고, 토스 취소 요청에는 동일 결제 재시도에 사용할 멱등 키를 둔다. 완료 결과는 canceled 또는 cancel_failed로 기록한다. 취소 실패는 관리자 카드 결제 화면에 계속 노출하고, 해당 화면에서 실제 취소 상태를 확인한 뒤 안전하게 재시도하거나 수동 처리할 수 있게 한다. 고객에게는 취소 여부가 확인되지 않은 상태를 성공으로 표현하지 않는다.

### B. 민감 URL과 관리자 렌더링

비밀번호 재설정 화면은 분석·광고 스크립트를 로드하지 않는다. 결제 성공 화면은 head의 첫 스크립트에서 paymentKey, orderId, amount를 메모리에만 복사하고 즉시 query string을 제거한 뒤 기존 분석 스크립트를 로드한다. 결제 확인 요청은 메모리 값으로 보낸다. 결제 승인 API 파라미터와 결제 완료 UI는 유지한다. public/track.js의 동작은 변경하지 않는다.

관리자 회원·주문 화면에서 DB 또는 API 값은 innerHTML 문자열 템플릿으로 삽입하지 않는다. 텍스트 노드와 안전한 DOM 속성을 사용하고, 상태·클래스 값은 허용 목록에서 선택한다. 회원 가입 email은 공백 제거, 길이 제한 및 형식 검증을 추가한다. OAuth 이름도 출력 시 동일하게 신뢰하지 않는다.

### C. 개인정보 보존과 계정 탈퇴

결제 준비 상태의 form_json은 준비 후 30분이 지나면 삭제한다. 상품 생성이 시작되어 해당 job_id가 결제 행에 연결되면 form_json과 광고 attribution을 비운다. 생성된 고객 결과는 정상적인 주문 내역/재다운로드 목적에 필요한 동안만 보유한다.

마이페이지에 탈퇴 요청과 완료 절차를 제공한다. 로그인 세션만으로 파기하지 않고, 로컬 비밀번호 재확인 또는 로그인 제공자 재인증/검증된 이메일의 일회용 확인으로 본인을 확인한다. 활성 결제·환불·생성 작업이 있으면 해당 상태를 먼저 정리하거나 명확한 완료 시점을 안내한다.

탈퇴 완료 시 프로필, 세션, 인증·재설정 토큰, OAuth 연결 식별자, 생성 파일, 결과 본문/시각 자료, 준비 폼과 광고 유입 정보를 삭제한다. 결제·환불·공급 기록에 필요한 최소 주문번호, 상품, 금액, 상태, 시각과 거래 참조값은 개인 계정 정보 및 결과 데이터와 분리해 보존 기간을 기록하고 기한 후 파기한다. 개인정보 처리방침의 저장 목적·기간·수탁자(메일 발송 포함)와 탈퇴 방법을 실제 동작에 맞게 고친다. 법정 보존 기록의 범위와 기간은 현재 법령에 맞춰 구현 전 재확인한다.

구현 계획 작성 시 확인한 현행 기준(2026-10-11): 개인정보 보호법 제21조는 목적 달성 등 불필요한 개인정보의 지체 없는 파기와 법정 보존 데이터의 별도 저장·관리를 요구한다. 전자상거래법 시행령 제6조는 계약/청약철회 및 대금결제/재화 공급 기록 5년, 소비자 불만/분쟁처리 기록 3년을 정한다. 실제 서비스에서 보유하는 거래 유형만 최소 항목으로 보존한다.

### D. 백업, 세션, 저장소 및 요청 제한

DB 백업 메일 첨부는 AES-256-GCM으로 암호화하고, 별도 BACKUP_ENCRYPTION_KEY가 없거나 형식이 잘못되면 평문 백업을 보내지 않고 실패시킨다. 임시 DB와 암호문 파일은 성공·실패 모두 finally에서 정리한다. 운영자가 복원할 수 있도록 복호화 절차와 키 보관·교체 방법을 문서화한다.

운영에서는 기본 세션 비밀값을 거부하고 충분히 긴 SESSION_SECRET을 필수화한다. OUTPUT_DIR이 없거나 쓰기 불가하면 경고만 남기지 않고 시작 점검에 실패하게 한다. 실제 영구 볼륨 연결 여부는 배포 플랫폼 설정에서 별도로 확인해야 한다. 결제 준비와 인증 메일 재발송은 계정/IP 기준 요청 제한을 둔다.

### E. 의존성

잠금 파일 기준으로 npm audit을 다시 실행하고 패치 가능한 하위 의존성을 업데이트한다. audit의 현재 강제 수정은 Puppeteer 25.13.0 주요 버전 변경을 요구한다. Puppeteer 브라우저 설치, PDF 생성, 이미지 작업 및 서버가 사용할 Node 런타임 호환성을 확인한 다음 업데이트한다. 호환성 확인 없이 force 설치는 하지 않는다. 현재 저장소에는 Node 버전 또는 Render 배포 설정 파일이 확인되지 않았으므로, 지원 Node 버전을 명시하고 배포 환경도 같은 버전으로 맞춘다.

## 4. 배포 순서와 카드사 심사 조건

심사 중인 사이트의 구매 경로가 달라지지 않도록 변경을 두 묶음으로 배포한다.

1. 심사 중: 결제 상태·복구, 관리자 안전 렌더링, 민감 URL 정리, 백업 암호화, 운영 설정 검증, 요청 제한과 의존성 업데이트를 구현·검증한다. 상품/가격/결제 위젯/약관·환불 안내/사업자 하단 정보 및 토스 success/fail URL은 유지한다. 공개 문구나 탈퇴 UI는 아직 배포하지 않는다.
2. 두 카드사 승인 완료 후: 개인정보 처리방침과 계정 탈퇴 화면·안내를 공개한다. 거래 기록 분리와 삭제 동작을 확인한 뒤 함께 배포한다.

실제 운영 환경의 환경변수와 영구 저장 경로는 배포 전에 확인해야 한다. 누락 여부를 모르는 상태에서 fail-fast 변경을 운영에 배포하지 않는다. 어떠한 운영 배포도 이 설계 승인만으로 자동 실행하지 않는다.

## 5. 실패 처리와 고객 안내

- 결제 승인 여부가 확인되지 않으면 고객에게 결과 확인 중임을 알리고 같은 주문으로 재확인할 수 있게 한다.
- 자동 취소가 실패하면 주문을 수동 환불 필요 상태에 유지하고 관리자 화면에 이유와 주문번호를 보여준다.
- 백업 키가 없거나 암호화·메일 발송이 실패하면 백업 실패를 관리자에게 알리며 평문으로 대체하지 않는다.
- 저장 경로 및 운영 비밀값이 누락되면 배포 설정 누락을 로그에 남기고 서비스 시작을 차단한다.
- 계정 탈퇴가 진행 중 주문 때문에 보류되면 고객에게 해당 주문 상태와 재요청 방법을 안내한다.

## 6. 검증 기준

수정 전에 회귀 테스트를 작성한다. 결제 승인 응답 유실 후 조회 복구, 중복 confirm, 프로세스 재시작 뒤 job 연결, 중복 시작 방지, 토스 취소 실패 상태, form 만료/삭제를 검증한다. HTML 계약 테스트로 reset 화면에 분석 태그가 없고 pay-success가 추적기보다 먼저 query를 제거하는지 확인한다. XSS 페이로드는 관리자 표에서 텍스트로만 보이는지 검사한다. 탈퇴는 검증 절차, 서비스 데이터 파기, 최소 거래 기록 잔존 및 기간 만료 삭제를 테스트한다. 백업은 암호화, 복호화, 키 누락 차단과 임시 파일 정리를 검증한다.

전체 npm test, PDF/이미지 생성 확인, npm audit 재실행, 테스트 키 결제 성공·실패·취소 흐름을 수행한다. 실카드 결제는 승인 상태 확인 전까지 시도하지 않는다. 카드사 승인 전에 실제 운영에 반영할 경우, 상품·가격·결제창·약관·푸터가 기준 화면과 같은지 확인한다.

## 7. 범위 밖

- 상품 가격, 판매 설명, 결제 수단 또는 토스 계약/MID/키를 변경하지 않는다.
- 카드사 심사 현황을 대신 변경하거나 카드사·토스에 문의하지 않는다.
- 배포 플랫폼의 실제 비밀값, 영구 볼륨 또는 기존 백업 메일함은 이 저장소에서 변경할 수 없다.
- 계정 삭제 후 법정 보존이 필요한 거래기록의 구체적 항목과 보존 기산일은 구현 계획에서 현재 법령 및 실제 회계 처리 기준을 대조한다.
