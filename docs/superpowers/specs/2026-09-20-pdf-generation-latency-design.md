# PDF 생성 대기시간 개선 설계

작성일 2026-09-20 · 상태 검토 대기

## 1. 문제

평생사주 100p 리포트는 결제부터 PDF 완성까지 10~20분이 걸린다(운영자 확인값).
그동안 고객 화면에는 진행률 말고 볼 것이 없다. 14,900원을 결제한 직후가 이탈이
가장 쉬운 구간인데, 그 구간이 가장 길고 가장 비어 있다.

원인은 PDF 렌더링이 아니라 LLM 호출 구조다. renderPdf는 Puppeteer 실행부터 종료까지
10~20초로 전체의 1%대다.

## 2. 현황 분석

src/llm/generateReport.js의 CONCURRENCY = 1 이 병목이다. 18개 챕터를 한 번에 하나씩
순차로 부른다. 챕터 하나의 목표 분량이 약 5,500자이므로 출력 4,000~5,000 토큰,
호출당 60~80초다. 18개면 20분 안팎이 된다.

순차 구조가 지키는 것은 priorSummaries 하나뿐이다. 앞 챕터들의 요약을 다음 챕터
프롬프트에 넣어 같은 이야기가 반복되는 것을 막는다. 주석에 따르면 예전에 3개씩
병렬로 돌렸을 때 같은 배치 안의 챕터끼리 서로를 보지 못해 내용이 겹쳤고, 그래서
속도를 포기했다.

약한 제약 하나 때문에 18단 깊이의 의존 사슬이 생긴 셈이다. 게다가 이 사슬은 맥락을
불공평하게 나눠준다. 챕터 1은 아무 맥락 없이 쓰이고 챕터 18은 앞선 17개 요약을 전부
본다.

부수 문제도 있다. client.js의 max_tokens가 챕터 목표 분량과 무관하게 전부 12,000이다.
응답이 한도에서 잘리면 stop_reason 검사에 걸려 통째로 버리고 처음부터 다시 부른다.
한 번 걸릴 때마다 1~2분이 사라진다.

3,900원 심층 리딩도 같은 패턴이다. 대부분 주제는 챕터 1개와 시기 분석 1개로 2회
순차라 2~3분이지만, 내 사주 첫 풀이는 챕터 3개와 시기 1개로 4회 순차다.

## 3. 목표

- 평생사주 100p 생성 시간을 10~20분에서 5분 이내로 줄인다.
- 결제 직후부터 고객이 볼 것이 있게 한다. 완본을 기다리는 동안 빈 화면이 없어야 한다.
- 본문 품질은 떨어뜨리지 않는다. 중복 서술은 현재보다 줄어야 한다.

성공 기준은 같은 생년월일시로 생성했을 때 완료까지 5분 이내, 결제 후 첫 콘텐츠
노출까지 10초 이내, 챕터 간 중복 문장 비율이 현재 이하인 것이다.

## 4. 제약

Anthropic API 티어를 모른다. 분당 출력 토큰 한도(OTPM)가 병렬 수를 결정하는데 그 값을
사전에 알 수 없다.

다만 API 응답 헤더가 실제 한도를 알려준다.

- anthropic-ratelimit-output-tokens-limit : 현재 한도
- anthropic-ratelimit-output-tokens-remaining : 남은 양
- anthropic-ratelimit-output-tokens-reset : 회복 시각
- 429 응답의 retry-after : 대기 초

한도는 토큰 버킷 방식으로 연속 적용되고, OTPM은 max_tokens가 아니라 실제 생성된
토큰으로 계산된다.

이 값을 런타임에 읽어 동시성을 스스로 맞추면 티어를 몰라도 안전하다. 동시에 진단도
된다. 18챕터의 총 출력이 약 81,000 토큰인데, 한도가 수십만 단위로 넉넉하면 현재 느린
이유는 순차 구조다. 반대로 한도가 1만 미만이면 애초에 분당 토큰 한도에 막혀 있던
것이고, 그 경우 병렬화만으로는 해결되지 않아 티어 상향이 선행 과제가 된다. 이 구분을
코드가 알려주게 만든다.

## 5. 설계

### A. 배분표 + 병렬 집필

순차 사슬을 두 단계로 바꾼다.

1단계는 짧은 호출 한 번으로 18개 챕터의 배분표를 만든다. 각 챕터가 무엇을 다루고
무엇을 다루지 않을지, 어떤 근거를 어느 챕터에서 쓸지 정한다. 출력이 작아 15초 내외로
끝난다.

2단계는 그 배분표 전체를 모든 챕터에 컨텍스트로 넣고 병렬로 집필한다.

priorSummaries는 제거한다. 다만 이것이 강한 장치를 약한 장치로 바꾸는 것은 아니다.
현재 summarize()는 5,500자 본문에서 첫 두 문장, 최대 120자만 뽑아 넘긴다. 즉 앞 챕터가
무엇을 다뤘는지가 아니라 어떻게 시작했는지만 전달된다. 챕터 18이 받는 정보는 17개의
120자 오프닝 조각이 전부다. 중복 방지 장치로서 신호가 매우 얇다. 같은 코드베이스의
deepReading이 마지막 문단 300자(핵심 요약)를 넘기는 것과 비교해도 약하다.

배분표는 어느 챕터가 어떤 소재를 맡는지 명시하므로 120자 오프닝보다 강한 제약이고,
앞뒤 양방향으로 작동한다. 맥락 불공평도 사라진다.

그래도 배분표만으로 해결되지 않는 중복이 둘 있다.

첫째는 공통 근거 반복이다. 모든 챕터가 같은 명식에서 출발하므로 재물 챕터도 직업
챕터도 일간과 용신 설명을 도입부에 깔 수 있다. 실무에서 가장 흔한 중복이고 현재
구조에서도 이미 발생하고 있을 가능성이 높다. 이건 배분표가 아니라 명시적 규칙으로
막는다. 명식 기초 해설은 1~3장에서만 하고 이후 챕터는 결론 한 줄만 참조하도록
시스템 프롬프트에 못박는다.

둘째는 표현 중복이다. 같은 모델과 같은 시스템 프롬프트를 쓰므로 문단 구조와 상투구가
닮는다. 병렬이라서 나빠지지는 않지만 배분표로 좋아지지도 않는다.

이 둘이 측정에서 잡히면 3단계로 교정 패스를 추가한다. 완성된 18챕터를 한 번에 스캔해
겹치는 대목만 다시 쓰게 하는 호출 1~2회다. 전체 시간에 미치는 영향이 작으므로
필요할 때 넣는다. 미리 넣지는 않는다.

실패 복구는 지금 방식을 유지한다. chapters.json에 완료분을 증분 저장하고 재시작 시
이어받는다. 배분표도 같은 폴더에 저장해 재시도할 때 다시 만들지 않는다.

### B. 적응형 동시성

client.js에 동시성 제어를 넣는다.

- 시작 동시성 3
- 매 응답에서 rate limit 헤더를 읽어 기록한다
- 남은 출력 토큰이 한 배치분(현재 동시성 × 챕터당 예상 출력 토큰)의 3배 이상이면
  동시성을 1 올린다. 상한 6
- 429를 받으면 동시성을 절반으로 줄이고 retry-after만큼 기다린 뒤 재시도한다

현재 재시도 로직은 2회, 1초와 2초 고정 대기이고 retry-after를 무시한다. 병렬화하면
429가 정상적으로 발생하므로 이 부분을 먼저 고쳐야 한다. 고치지 않고 병렬만 켜면 429가
실패로 처리되어 주문이 환불되는 회귀가 생긴다.

관측한 한도는 주문 로그에 남겨 티어를 역산할 수 있게 한다.

### C. max_tokens 정밀화

챕터별 목표 분량에서 max_tokens를 계산한다. 한국어는 토큰당 1~1.5자이므로 목표
글자수에 1.6배 정도 여유를 둔 값을 쓴다. 5,500자 목표면 약 6,000 토큰이다.

출력 토큰이 곧 시간이자 비용이므로 한도를 좁히면 둘 다 줄고, 모델이 분량 감각을 갖게
되어 잘림 재시도도 덜 난다.

### D. 체감 시간

두 가지를 순서대로 한다.

요약 카드를 주문 직후로 옮긴다. summary-card.png는 명식 계산 결과만으로 만들어져 LLM이
필요 없는데, 지금은 PDF가 다 나온 뒤 마지막에 만든다. 주문 직후로 옮기면 결제 후 몇 초
안에 볼 것이 생긴다.

완성된 챕터부터 웹에서 읽게 한다. chapters.json 증분 저장과 orders.updateProgress가 이미
있어 토대는 깔려 있다. /api/status가 완료된 챕터 본문을 함께 내려주고 결과 페이지가
그것을 이어붙여 보여주면 된다. PDF는 뒤따라온다.

결과적으로 흐름이 이렇게 바뀐다.

| 시점 | 현재 | 개선 후 |
|---|---|---|
| 결제 직후 | 진행률 0% | 요약 카드 |
| 1분 | 진행률 5% | 첫 챕터 읽기 시작 |
| 5분 | 진행률 25% | 완본 PDF |
| 10~20분 | 완본 PDF | 이미 끝남 |

## 6. 적용 범위

평생사주 100p를 먼저 한다. 효과가 가장 크고 구조가 가장 단순하다.

심층 리딩의 내 사주 첫 풀이는 같은 방식을 적용한다. 챕터가 3개라 배분표 없이 병렬만
해도 되지만 같은 코드 경로를 쓰므로 자연히 따라온다. 나머지 단일 호출 상품은 건드리지
않는다.

## 7. 검증

병렬화 전후로 같은 입력(생년월일시 고정)의 결과를 비교한다.

- 완료까지 걸린 시간
- 챕터별 출력 토큰과 총 원가
- 챕터 간 중복도. 20자 이상 연속 일치하는 문자열의 총량과, 문장 단위 유사도 상위 쌍을
  뽑는 스크립트로 잰다. 병렬화에 손대기 전에 현재 구조로 1건 생성해 기준선을 먼저
  확보한다. 기준선 없이 바꾸면 좋아졌는지 나빠졌는지 말할 수 없다
- 429 발생 시 환불되지 않고 재시도로 복구되는지
- 중간 실패 후 재시작이 완료분을 이어받는지

중복 비율이 현재보다 나빠지면 배분표 프롬프트를 고치고, 그래도 안 되면 되돌린다.

## 8. 범위 밖

Puppeteer 브라우저 상주화는 1~3초짜리라 지금 손댈 가치가 없다. 모델을 더 빠른 쪽으로
낮추는 것도 하지 않는다. 14,900원 상품의 본문 품질을 속도와 맞바꾸는 선택이기 때문이다.

## 9. 순서

1. 재시도 로직 수정 — retry-after 준수, 429를 실패로 처리하지 않음
2. rate limit 헤더 기록 — 실제 티어 확인
3. 배분표 생성과 병렬 집필 전환
4. max_tokens 정밀화
5. 요약 카드 선출력
6. 완성 챕터 부분 전달

1과 2는 병렬화의 전제라 먼저 해야 한다. 2의 결과에 따라 3의 동시성 상한이 정해지고,
한도가 낮게 나오면 티어 상향이 선행 과제가 된다.
