# 설계 결정 및 출처

## 천을귀인(天乙貴人) / 문창귀인(文昌貴人) 매핑표

여러 명리학 자료마다 세부 지지가 조금씩 다르다(특히 천을귀인의 庚/辛 배속). 본 프로젝트는
가장 널리 통용되는 **자평진전·삼명통회 계열 표준표**를 채택한다 (`src/engine/shinsal.js`):

- 천을귀인: 甲戊庚→丑未, 乙己→子申, 丙丁→亥酉, 辛→寅午, 壬癸→巳卯
- 문창귀인: 甲→巳, 乙→午, 丙戊→申, 丁己→酉, 庚→亥, 辛→子, 壬→寅, 癸→卯

다른 학파의 표를 쓰고 싶다면 `src/engine/shinsal.js`의 `CHEONEUL`/`MUNCHANG` 테이블만 교체하면 된다.

## 형충회합 우선순위 규칙

- 삼합/방합이 **완전체(3글자 전부)**로 성립하면, 그 지지들이 걸린 육합·충은 삭제하지 않고
  `weakened: true` 태그만 붙인다 (서술 단계에서 "합이 있지만 삼합에 묶여 힘을 못 씀" 뉘앙스를 낼 수 있도록).
- 반합은 왕지(旺支, 삼합/방합 그룹의 가운데 글자)가 반드시 포함되어야 성립한다 (예: 申子辰 중 申辰만 있고 子가 없으면 반합 불인정).
- 형(刑) 중 삼형(무은지형 寅巳申, 무례지형 丑戌未)은 2글자 이상 겹치면 성립으로 보되 `complete` 필드로 3글자 완전성 여부를 구분한다.
- 자형(辰午酉亥)은 같은 지지가 사주 내에 2개 이상 나타날 때만 성립.

## 종격(從格) 처리 범위

v1은 종격을 **후보 플래그 + 유형 추정**까지만 낸다 (전면적인 종격 확정 판정은 범위 밖).
조건: 신약 판정 + 득령·득지·득세·통근 전부 실패 + 사주 8글자(연월일시 천간+지지 정기) 중 한
오행이 5개 이상. 이 경우 `kyukguk.jonggyeok = { candidate: true, type, dominantOhaeng }`.

## 조후용신 규칙표 (v1, 최소 구현)

- 겨울생(월지 亥子丑) + 水 오행 개수 3개 이상 → 조후용신 火
- 여름생(월지 巳午未) + 火 오행 개수 3개 이상 → 조후용신 水
- 봄/가을생은 v1에서 조후 트리거 없음 (추후 확장 여지로 남김)

## 정확성 교차검증

`strength`/`kyukguk`/`yongshin`/`shinsal` 단위테스트는 "코드가 자기 규칙과 일치하는지"만
증명한다. 실제 명리학적 정확성은 Phase 1 구현 중 팔자(八字) 원본 계산(lunar-javascript가
전담, Phase 0에서 구 엔진과 바이트 단위로 동일함을 이미 확인)을 독립 출처로 교차검증했다.

**샘플: 1990-05-15 10:30(양력, 서울 경도보정 −32분 적용/미적용 모두 09:30~11:30 巳시 범위라 동일)**

- 엔진 출력: 연주 庚午 · 월주 辛巳 · 일주 庚辰 · 시주 辛巳
- 연주 庚午 ✅ — "1990년은 백말띠(白말띠) = 경오(庚午)년"이라는 사실이 나무위키 등 다수 출처에서
  널리 확인됨(1990년생이 대규모 성비 불균형을 낳은 '백말띠 미신'의 그 해).
- 일주 庚辰 ✅ — 나무위키 "경진(간지)" 문서가 "1990년의 경진일은 1월 15일, 3월 16일,
  **5월 15일**, 7월 14일, 9월 12일, 11월 11일"이라고 명시. 다음날(5/16)이 나무위키
  "신사(간지)" 문서에서 확인되는 것과도 60갑자 순서상 정합(庚辰→辛巳).
- 월주 辛巳 ✅ — 오호둔법(五虎遁法) 수동 검산: 년간 庚(乙庚년) 기준 인월(寅月)은 戊寅부터
  시작 → 卯월 己卯 → 辰월 庚辰 → **巳월 辛巳**. 5월 15일은 입하(立夏, 巳월 시작 ~5월 5일경)
  이후이므로 巳월이 맞고, 월주가 辛巳로 일치.
- 시주는 별도 독립 검증은 못 했으나 동일 라이브러리(EightChar)의 동일 오자둔법 계산 경로이므로
  위 세 기둥이 검증된 이상 신뢰도 높음.

이 결과로 Phase 0/1의 팔자 원본 계산 신뢰성을 확인했고, 그 위에 쌓은 `strength`/`kyukguk`/
`yongshin`/`hapchung`/`shinsal`의 25개 단위테스트(모두 통과)는 이 문서에 명문화된 규칙과
코드가 일치함을 보장한다.

## 페이지 분량 보정 (Phase 6/7 실측)

최초 CSS(11pt/줄간격1.8/여백20mm)로는 약 2,550자당 1페이지가 나와, 100페이지를 채우려면
챕터당 7,000~14,000자가 필요했다 — LLM 출력량·비용이 지나치게 커지는 문제. 사용자 선택에
따라 **CSS로 페이지당 분량을 줄이는 방향**으로 해결:

- `report.css`: 폰트 13pt(11→13), 줄간격 2.5(1.8→2.5), 페이지 여백 26mm(18~20mm→26mm),
  문단 간격 9mm(4mm→9mm)로 확대.
- 재측정 결과: **약 857자당 1페이지** (6,000자 채운 챕터 1개로 정밀 측정).
- 이에 맞춰 `src/llm/chapters.js`의 `targetWords`를 챕터당 2,300~4,650자로 재조정
  (원래 300~600자 배치의 상대 비중은 유지, 스케일만 약 7.75배 확대).
- 최종 더미 텍스트로 전체 렌더링 검증: **94페이지** (100±15 목표 범위 내).
- `src/llm/client.js`의 `max_tokens`를 4000→8000으로 상향(챕터당 최대 4,650자 출력 여유 확보).

측정 스크립트: `test/manual-page-calibration.js`(빈 챕터 기준선), `test/manual-page-calibration2.js`
(단일 챕터 정밀 측정), `test/manual-render-pdf.js`(전체 검증).

## PDF 디자인 — 천문성좌(다크) 테마 (2차 개편)

사용자가 "흔한 AI 느낌"을 명시적으로 거부해 3가지 표지 시안(한지·먹 / 천문성좌 / 모던 에디토리얼)을
만들어 비교했고, **천문성좌(별자리) 다크 테마**로 확정했다. 핵심 요소:

- 연/월/일/시 네 기둥을 별자리 점으로 배치(`src/pdf/starchart.js`)하고, **장식이 아니라 실제
  `hapchung`(형충회합) 계산 결과**로 점 사이 연결선을 그린다 — 육합은 금빛 실선, 충은 적갈빛
  파선, 나머지는 옅은 회청빛 기본 그리드. 오행별 점 색상도 `charts.js`의 팔레트와 통일.
- 배경은 순수 CSS 반복 `radial-gradient`로 만든 별무늬(이미지 자산 없음, 파일 용량 안 늘어남).

### Puppeteer 함정 — `@page { margin }`이 JS `margin` 옵션을 덮어씀

다크 테마를 좌우 끝까지 채우려고 "@page 여백은 0, 본문 CSS padding으로 여백 대체" 방식을 썼는데,
`@page { margin: 0; }`을 CSS에 넣어두면 **Puppeteer `page.pdf({margin})`으로 넘긴 top/bottom
값이 통째로 무시되고 0으로 고정되는 버그성 동작**을 실측으로 확인했다(`test/manual-margin-sanity*.js`
세 스크립트로 격리 재현). 해결: `@page`에는 `size`만 지정하고 `margin`은 아예 언급하지 않는다 —
margin 제어는 전적으로 `renderPdf.js`의 JS `margin` 옵션에 맡긴다.

또한 Puppeteer는 **좌우 margin 영역을 칠할 방법이 없다**(header/footerTemplate은 상/하단에만
적용됨). 그래서 좌우 margin=0 + 본문 CSS padding(26mm)으로 여백을 대신하고, 상/하 margin(20mm/24mm)은
header/footerTemplate 자체에 다크 배경(`background-color` + 인라인
`-webkit-print-color-adjust:exact`)을 칠해 페이지 전체가 이어져 보이게 했다 — 이 인쇄용 색상 강제
출력 속성을 template 내부에 다시 넣지 않으면(전역 CSS만으로는 부족) 헤더/푸터가 흰 배경으로 나온다.

최종 확인: 별자리 다이어그램, 명식표, 챕터 전환부(페이지 30번대) 모두 다크 배경이 끊김 없이
이어지고, 챕터 목표 재조정 없이 95페이지로 100±15 범위 유지.

### 추가 수정 — 헤더/푸터 여백에 흰 줄이 남던 문제

사용자가 실제로 받은 PDF를 열어보니 페이지마다 위/아래에 얇은 흰 줄이 남아 있었다. 원인은
header/footerTemplate의 배경 div를 `height:20mm`/`height:24mm` 같은 고정 mm 값으로 지정했을 때,
Puppeteer가 계산하는 실제 여백 상자 크기와 mm→px 변환 과정에서 미세한 반올림 차이가 생겨
1px 안팎의 미도색 틈이 남는 것이었다. 해결: 템플릿 div를 `position:fixed; top/left/right/bottom:-1mm`
로 여백 상자보다 살짝(1mm) 더 크게 오버스캔시켜 어떤 반올림 오차에도 완전히 덮이도록 했고,
템플릿 자체의 `html,body{margin:0;padding:0;}`도 함께 리셋했다(Puppeteer가 헤더/푸터 템플릿에
자체 기본 여백을 주는 경우가 있어 이것도 틈의 원인이 될 수 있음). `test/manual-screenshot-pdf.js`를
PDF.js의 "page-fit" 모드로 페이지 경계를 단독으로 캡처하도록 고쳐서, 뷰어가 페이지 사이에 그리는
장식용 구분선과 실제 페이지 내부의 흰 여백을 구분해 검증했다.

### ⚠️ 심각한 회귀 — `position:fixed` 오버스캔이 본문을 통째로 가림

위 흰 줄 수정을 위해 header/footerTemplate 배경 div를 `position:fixed; top/left/right/bottom:-1mm`
로 바꿨더니, **Puppeteer/Chromium 자체 뷰어에서는 정상으로 보이지만 다른 모든 PDF 렌더러(사용자가
연 여러 앱, 그리고 완전히 독립적인 MuPDF)에서는 본문 전체(제목·별자리·표·챕터 텍스트 전부)가
사라지고 배경과 푸터만 남는 심각한 버그**가 발생했다. Chromium의 PDF 뷰어(PDFium)만 유독 관대하게
렌더링해서 이 문제를 자체 검증(Chromium으로 PDF를 열어 스크린샷) 단계에서 놓쳤다 — **PDF를
생성한 것과 같은 엔진으로 다시 열어 "검증"하는 방식 자체가 이런 종류의 버그를 가려버릴 수 있다는
교훈.**

추정 원인: header/footerTemplate 안에서 `position:fixed`는 그 작은 여백 상자가 아니라 사실상
페이지 전체를 기준으로 배치되어, 다크 배경 사각형이 여백을 넘어 페이지 전체를 덮는 별도 오버레이
레이어로 그려지고, 이 레이어가 본문 콘텐츠 레이어보다 나중에(위에) 합성되면서 엄격한 PDF 파서에서
본문을 완전히 가린 것으로 보인다.

**해결**: `position:fixed` 오버스캔을 포기하고, 원래의 단순한 박스 모델(`width:100%;height:20mm`
/`height:24mm`, 일반 정적 배치)로 되돌렸다. 미세한 흰 선 하나(코스메틱)보다 본문이 모든 뷰어에서
보이는 것(기능적 정합성)이 훨씬 중요하다는 우선순위로 판단.

**검증 방법 교훈**: PDF 렌더링 문제는 **생성에 사용한 엔진과 다른 독립 렌더러**로 반드시
교차검증해야 한다. 이 프로젝트에서는 Python의 `pymupdf`(MuPDF, Chromium과 무관한 C 라이브러리)로
`page.get_pixmap()`을 이용해 페이지를 실제 래스터 이미지로 뽑아 확인했다 —
`test/manual-minimal-repro.js`(최소 재현) + 인라인 python 스크립트로 여러 페이지를 검증.

### 흰 줄의 정체 — Chromium이 header/footerTemplate에 강제하는 고정 인셋(~5.42mm)

`position:fixed` 회귀를 되돌린 뒤에도 페이지 상/하단에 흰 줄이 남아 있었다. `margin.top`을
10mm/20mm/40mm로 각각 바꿔가며 `test/manual-margin-scaling-test.js` + `test/measure_gap.py`
(PyMuPDF로 페이지 상단부터 실제 배경색(14,19,32)이 처음 나타나는 행을 픽셀 단위로 탐색)로
측정한 결과, **흰 틈의 크기가 margin 값과 무관하게 항상 정확히 5.42mm로 고정**되어 있음을
확인했다. 즉 이것은 CSS 여백 리셋이나 반올림 오차가 아니라, **Chromium/Puppeteer가
header/footerTemplate 콘텐츠 자체를 실제 페이지 가장자리에서 고정폭만큼 안쪽으로 강제 삽입하고
그 바깥은 어떤 CSS로도 칠할 수 없는 하드코딩된 플랫폼 동작**이다(상/하 대칭, 좌우 margin=0 +
본문 padding으로 만드는 여백은 이 문제가 없음 — 오직 header/footerTemplate 메커니즘만 영향받음).

**대응**: 이 5.42mm는 없앨 수 없으므로, 없애려 하지 않고 **margin 자체를 필요한 최소값까지
줄여 이 고정 인셋이 곧 전체 여백이 되도록** 했다(`renderPdf.js`: margin.top 20mm→9mm,
margin.bottom 24mm→14mm). 그리고 그 경계(다크 배경이 시작되는 지점)에 `border-bottom`/
`border-top: 0.4mm solid var(--gold)` 얇은 금색 선을 그어, 여백 사고처럼 보이지 않고
의도적으로 디자인된 테두리처럼 보이게 만들었다. 재측정 결과 흰 틈은 여전히 ~5.3~5.42mm로
동일(더 줄일 수 없는 하한)이지만, 전체 여백이 얇아지고 금색 선으로 마감되어 시각적으로는
"흰 줄 버그"가 아니라 "얇은 금박 테두리"로 읽힌다. margin을 줄이면서 페이지당 사용 가능한
본문 영역이 늘어나 총 페이지 수가 ~99p → ~87p로 줄었다.

**페이지 수 복원(87p → 99p)**: targetWords(챕터별 목표 분량)를 올려 텍스트를 늘리는 방식은
쓰지 않았다 — 사용자가 이미 "글자수만 늘려서 반복/억지 내용으로 채우는 결과물은 원치 않는다"고
못 박은 바 있고, targetWords를 건드리면 18챕터 전체를 LLM으로 재생성해야 해서 그 위험을
다시 감수하게 된다. 대신 `body`의 `line-height`를 2.5 → 2.85로만 올렸다 — 이건 순수 타이포그래피
조정으로 실제 글자 수는 한 글자도 늘지 않았고, 동일한 `chapters.json`(재생성 없음)으로
`test/manual-render-only.js`를 다시 돌려 페이지 수만 87 → 99로 복원했다. 줄간격이 늘어난
가독성도 스크린샷으로 확인(너무 성글어 보이지 않음).

### 챕터 연속 페이지 상단에서 본문 첫 줄이 금색 선에 붙어 잘려 보이던 문제

줄간격을 늘린 뒤, 챕터 "시작" 페이지가 아니라 내용이 이어지는 "연속" 페이지(문단 중간에
페이지가 넘어가는 경우)에서 본문 첫 줄이 헤더의 금색 선에 거의 맞닿아 위쪽이 잘려 보이는
문제가 발견됐다. `test/manual-render-only.js` + PyMuPDF로 특정 페이지(예: 8페이지)를
`dpi=200~400`으로 크롭/줌해서 재현에 성공했다 — 챕터 시작 페이지는 `.chapter`의
`padding-top:18mm`가 있어 문제가 없었지만, 연속 페이지는 본문이 margin.top 경계에 거의
바로 붙어 시작해 여유가 없었다.

**두 번의 잘못된 시도와 원인**:
1. `margin.top`을 9mm→14mm로 늘려봤지만 선과 글자가 "함께" 밀려날 뿐 둘 사이 간격은
   전혀 좁혀지지 않았다(margin은 이미 5.42mm 강제 인셋 문제로 최소화해둔 상태라, 단순히
   키우면 백지 여백만 늘 뿐 이 문제는 해결 못 함).
2. 금색 선을 그리는 자식 `<div>`에 `margin-top`(flex 버전) 또는 부모에 `padding-top`을
   줘서 선을 안쪽으로 띄우려 했는데, PyMuPDF로 gold 픽셀 행과 텍스트 잉크의 실제 y좌표를
   측정해보니 의도한 값이 반영되지 않고 선이 계속 거의 같은 위치(margin 경계 바로 위)에
   나타났다. 원인은 **CSS margin collapsing**이었다 — 부모 div에 테두리/패딩이 없으면 자식의
   `margin-top`이 부모를 그냥 통과해버려 부모 자체가 그만큼 밀리고, 자식과 부모 사이에는
   공간이 생기지 않는다.

**진짜 원인**: Puppeteer의 headerTemplate/footerTemplate은 내부에서 어떤 CSS를 쓰든
그 콘텐츠 전체가 페이지의 실제 인쇄 영역 기준으로 **일정한 오프셋만큼 아래로 이동(shift)**된
채로 그려진다(앞서 발견한 5.42mm 강제 인셋과 같은 계열의 Chromium 내부 동작). `padding-top`
값을 0mm/9.6mm로 바꿔가며 실측한 결과 "절대 위치 = padding-top + 약 5.3mm"라는 선형 관계를
확인했다 — 즉 padding-top 자체는 정상 작동하지만, 결과물이 항상 그 고정 오프셋만큼 더
내려간 곳에 그려진다는 걸 몰라서 "값을 바꿔도 그대로"라고 오판했던 것.

**해결**: 위 선형관계를 역산해 헤더는 `padding-top: 4.3mm`(선이 본문 시작보다 충분히
위, 약 4~5mm 여유를 두고 그려지도록 계산), 푸터도 동일한 방식으로 캘리브레이션했다.
재렌더링 후 PyMuPDF로 (1) 금색 선의 정확한 행 위치, (2) 안티에일리어싱 잔상을 제외한
진짜 본문 텍스트의 시작 위치를 각각 측정해 확인했고, 200dpi 크롭 이미지로도 선과 텍스트
사이에 뚜렷한 여유 공간이 생겼음을 시각 확인했다. 표지(cover)의 `min-height`도 바뀐
margin 합계(14+18=32mm)에 맞춰 265mm로 재계산했다.

**교훈**: Puppeteer header/footerTemplate 내부의 위치 계산은 margin.top/bottom 값이나
일반적인 CSS 박스 모델 직관과 다르게 동작하는 부분이 있다(고정 인셋 + 선형 오프셋). 이
영역을 다시 조정할 일이 있다면, 반드시 픽셀 단위 실측(PyMuPDF)으로 "의도한 CSS 값이
실제로 그 위치에 반영됐는지"를 먼저 확인하고, 눈대중이나 저해상도 스크린샷만으로
"바뀌었다/안 바뀌었다"를 판단하지 않는다.

### 페이지 맨 위로 밀려난 차트(canvas)의 제목이 잘리는 문제

위 본문 텍스트 수정 이후, 명식 원국표 페이지의 오행 막대 차트(캔버스)가 새 페이지
맨 위로 넘어갔을 때 Chart.js가 캔버스 안에 그린 제목("오행 분포")의 위쪽이 헤더 바로
아래에서 잘려 보이는 문제가 추가로 발견됐다(같은 페이지의 십신 도넛 차트는 페이지
중간에 있어 멀쩡했고, 페이지 맨 위로 옮겨진 차트만 문제였다 — 위치 의존적이라는 것이
핵심 단서).

**원인**: `.chart-container`가 `margin: 6mm 0`으로 위쪽 여백을 주고 있었지만, 이 차트가
`avoid-break`에 의해 페이지 맨 위로 밀려날 때 그 top margin이 페이지 경계에서 사라졌다
(브라우저가 새 페이지를 시작하는 블록의 선행 margin을 소실시키는 것과 같은 종류의
현상 — 앞서 겪은 header/footerTemplate 안의 margin collapsing과는 별개의, 콘텐츠
쪽 여백에서 발생하는 현상). 캔버스는 텍스트처럼 자체 줄간격(leading)이 없어 이 여백이
없어지면 제목이 페이지 콘텐츠 경계에 완전히 붙어버렸다.

**해결**: `.chart-container`의 위아래 간격을 `margin`에서 `padding`으로 바꿨다(`padding:
7mm 0`) — padding은 페이지 경계에서 소실되지 않는다. 재렌더링 후 명식표 페이지(오행
막대 차트)와 7장 대운 차트(페이지 중간) 둘 다 스크린샷으로 확인해 제목이 완전하게
보이는 것을 확인했다.

**교훈**: `avoid-break`로 페이지 맨 위로 밀려날 수 있는 블록은 위쪽 여백을 `margin`이
아니라 `padding`으로 줘야 한다 — margin은 상황에 따라(부모-자식 collapse, 혹은 새
페이지 시작 시 소실) 신뢰할 수 없다.

### (가장 중요) 본문 텍스트가 실제로는 header/footer 다크 배경에 가려지고 있었던 문제

위 두 수정 이후에도 사용자가 Chrome과 알PDF에서 "여전히 잘린다"고 반복 제보했다.
이 저장소의 PyMuPDF 픽셀 스캔(색상 근사 매칭)으로는 몇 번을 다시 봐도 재현되지
않았다 — 바로 이 불일치가 실제 원인을 찾는 열쇠였다.

**진단 방법을 바꿈**: 픽셀을 스캔해 "그럴듯한 색"을 찾는 대신, `page.get_drawings()`로
PDF에 실제로 그려진 벡터 사각형의 **정확한 좌표**를 직접 뽑았다. 그 결과:
- 본문 배경 사각형: `[13.76mm, 279.14mm]` (이게 진짜 "본문 영역"의 경계)
- 헤더 다크 사각형(margin.top=14mm, div height=14mm일 때): `[5.29mm, 19.31mm]`
- 즉 헤더의 다크 배경이 본문 시작선(13.76mm)을 **5.5mm나 지나서까지** 그려지고 있었다.
- 푸터도 대칭적으로 본문 끝선(279.14mm)보다 5.3mm **먼저** 시작되고 있었다.

**원인**: header/footerTemplate 안의 콘텐츠 전체(다크 배경 포함)가 본문 쪽으로 고정
~5.3mm 이동해서 그려지는데(앞서 발견한 흰 틈/오프셋 현상과 같은 계열), 그동안 div의
`height`를 margin.top/bottom과 **동일하게** 설정해 와서, 이 이동분만큼 본문 영역을
침범한 채로 렌더링되고 있었다. PyMuPDF(MuPDF 엔진)는 이 겹침을 화면에 그대로
드러내지 않았지만(본문이 위에 합성되는 것처럼 보임), Chrome(PDFium)과 알PDF는 실제
PDF 콘텐츠 스트림 순서를 정직하게 따라 header/footer의 다크 사각형을 본문 위에 겹쳐
그려 첫/마지막 줄을 실제로 가렸다 — 그래서 사용자에게는 매번 "여전히 잘린다"로 보였고,
이쪽 검증 도구로는 재현되지 않았던 것.

**해결**: div의 `height`를 margin 값과 같게 두는 관행을 버리고, 이동량(~5.3mm)을 미리
뺀 값으로 줄였다 — 헤더 14mm→8mm, 푸터 18mm→11mm. 재렌더링 후 `get_drawings()`로
재확인한 결과 헤더 다크 사각형은 `[5.29, 13.23]`(본문 시작 13.76보다 0.53mm 앞에서
끝남), 푸터는 `[280.72, 291.84]`(본문 끝 279.14보다 1.58mm 뒤에서 시작함) — 이제 겹침이
전혀 없다. 이건 좌표상의 사실이라 어떤 PDF 렌더러로 열어도 겹칠 수 없다.

**교훈(가장 중요)**: 이번 세션에서 가장 크게 배운 점 — **자체 렌더러(PyMuPDF)로 "괜찮아
보인다"는 것은 증거가 아니다.** 겹침/은폐처럼 렌더러의 합성 순서에 따라 달라질 수 있는
버그는 픽셀을 스캔해 "보이는지"를 확인하는 것만으로는 절대 잡을 수 없고, 반드시
`get_drawings()`/`get_text()`로 뽑은 **좌표 자체가 겹치는지**를 기하학적으로 확인해야
한다. 사용자가 여러 번 재현된다고 말하는데 내 도구로는 재현이 안 될 때는, "내 눈에는
괜찮다"고 결론 내리지 말고 진단 방법 자체를 의심해야 한다.

### 일반 독자가 이해하기 어렵다는 피드백 — 전문용어 무설명 노출

PDF 렌더링 문제를 다 해결한 뒤, 사용자가 "일반인이 읽었을 때 무슨 말인지 이해할 수 없다"고
지적했다. 실제 1장 텍스트를 확인해보니 득령·득지·득세·통근·월지·여기(餘氣)·십신·비견 같은
명리학 전문용어가 설명 없이 그대로 쏟아지고 있었다(`interpretation.md`에는 "투출/폴백"
용어 하나만 풀어쓰라는 좁은 지시만 있었고, 나머지 전문용어 전반에는 적용되는 규칙이 없었음).

**해결**: `systemPrompt.js`에 일반 규칙 9번을 추가 — 명리학 전문용어(득령/득지/득세/통근,
십신 10종, 격국명, 억부/조후/통관/병약, 파격/종격, 12운성, 신살명, 궁위 용어 등)는 등장하는
"그 자리에서 즉시" 괄호나 짧은 구절로 풀어쓰도록 예시와 함께 명시했다. 독자를 "사주를 전혀
모르는 일반인"으로 가정하라고 명시.

**주의(재발 방지)**: `generateReport.js`는 `chapters.json`이 이미 있으면 챕터별로 재생성을
건너뛰는 재개(resume) 로직이 있다 — 시스템 프롬프트만 바꾸고 기존 `chapters.json`을 지우지
않은 채 재실행하면 API를 다시 호출하지 않고 예전 텍스트를 그대로 재사용해버린다(처음 한 번
이렇게 착각할 뻔했다 — "0.0초 소요"라는 로그가 재사용의 신호). 프롬프트/가드레일을 바꾼 뒤
재생성할 때는 반드시 대상 `chapters.json`을 먼저 삭제한다.

재생성 후 1장·15장을 직접 읽어 확인한 결과, 모든 전문용어가 처음 등장하는 자리에서 자연스러운
문장으로 풀어써졌다(예: "득령으로 태어난 달의 계절 기운을 내 편으로 얻었는가를 보는 것",
"비견(比肩, 나와 오행이 같고 음양도 같아 형제나 대등한 동료를 상징하는 기운)"). 분량이 늘어난
설명 때문에 페이지 수는 99 → 106으로 소폭 증가했는데, 이는 내용이 실질적으로 늘어난 것이지
글자 수를 억지로 채운 것이 아니므로(사용자가 이전에 명시한 "반복/억지 분량 늘리기 금지"
원칙과 무관) 정상적인 결과로 판단, 별도 조정 없이 유지.

### 흰 줄 문제 — 진짜 근본 해결 (header/footerTemplate 방식 폐기)

사용자가 정리해온 체크리스트(margin:0, printBackground:true, print-color-adjust:exact,
viewport 규격 고정 등 — 일반적인 "PDF 흰 여백" 문제의 표준 해법)를 계기로 재점검했다.
기존 접근(margin>0 + Chromium headerTemplate/footerTemplate으로 다크 배경 위장)은 이미
"5.3~5.4mm 강제 인셋" 버그를 여러 차례 우회해왔지만, 그 인셋 자체는 절대 없앨 수 없는
Chromium의 하드코딩된 동작이라는 게 이전 조사에서 이미 확인된 상태였다.

**실험(소형 2챕터 더미 문서로 8초 만에 비교)**:
- A안(기존, margin>0 + headerTemplate): 여전히 상하 각 5.3mm 흰 틈 존재(기존과 동일)
- B안(margin 전부 0, header/footer 없음): 배경은 완전 풀블리드(흰 틈 0mm)이지만, 연속
  페이지에서 본문이 페이지 상단에서 3.48mm밖에 안 떨어져 거의 가장자리에 붙어버림
  (섹션의 padding이 CSS 프래그먼테이션 규칙상 "그 섹션이 시작하는 첫 페이지"에만
  적용되고 이어지는 페이지에는 적용되지 않기 때문)
- D안(margin 0 + `box-decoration-break: clone`): 배경 풀블리드(0mm) + 연속 페이지도
  21.47mm로 균일한 여백 유지 — B안의 단점이 해결됨

**최종 채택**: margin을 상하좌우 전부 0으로 바꾸고(`renderPdf.js`), 여러 페이지에 걸쳐
이어질 수 있는 모든 섹션(`.chapter`, `.toc`, `.myeongsik`, `.compat-section`)에
`box-decoration-break: clone`(+`-webkit-` 접두사)을 추가했다. `page.get_drawings()`로
실제 배경 사각형이 모든 표본 페이지에서 `[0,0]~[210.08mm,297.13mm]`(페이지 전체)를
정확히 덮는 것을 확인 — 흰 틈이 좌표상으로 완전히 0이다.

**대신 잃는 것: 페이지 번호**. `displayHeaderFooter`는 margin>0이어야만 의미가 있어서
(margin=0이면 헤더/푸터가 그려질 공간 자체가 없음) 더는 Puppeteer의 헤더/푸터
메커니즘으로 페이지 번호를 넣을 수 없다. 대신 Puppeteer가 만든 완성 PDF를 `pdf-lib`로
열어 각 페이지 하단에 페이지 번호와 이름을 직접 그려 넣는 후처리 단계를 추가했다
(`renderPdf.js`의 `stampPageNumbers()`). 이 경로는 Chromium의 header/footer 렌더링을
전혀 타지 않으므로 애초에 그 버그와 무관하다.

**막힌 점 하나**: pdf-lib의 `StandardFonts.Helvetica` 같은 내장 폰트는 한글 글리프가
없어(WinAnsi 인코딩만 지원) 이름을 그대로 못 그린다 — 처음엔 비-ASCII 문자를 전부
"·"로 치환하는 임시방편을 썼다가, 그러면 실제 고객 이름이 다 점으로만 나오는 걸
깨닫고 되돌렸다. `@pdf-lib/fontkit`을 설치해 시스템에 있는 맑은 고딕 TTF
(`C:\Windows\Fonts\malgun.ttf`)를 직접 임베드하는 방식으로 고쳤다 — 이 프로젝트는
로컬 실행 전용이라 시스템 폰트 경로에 의존해도 괜찮다는 전제.

**참고**: `page.pdf()`가 반환한 버퍼를 pdf-lib로 다시 저장하면 내부 PDF 구조(객체
스트림 등)가 바뀌어서, 기존 테스트 스크립트들이 쓰던 정규식 기반 페이지 카운트
(`/Type\s*\/Page[^s]/g` 매칭)가 더는 정확하지 않다(0으로 나옴) — 실제 페이지 수
확인은 PyMuPDF(`len(fitz.open(path))`) 같은 진짜 PDF 파서로 해야 한다.
