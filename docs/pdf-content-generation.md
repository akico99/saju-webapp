# PDF 콘텐츠 생성 구조 감사 (2026-09-03)

이 문서는 "지금 이 앱이 만드는 PDF/리포트 본문이 실제로 어떤 코드·데이터로부터
만들어지는가"를 상품별로 정리한 것이다. 입력 폼의 필수/선택 여부가 아니라,
**본문 텍스트가 어떤 로직으로 채워지는지**에 초점을 맞춘다. 새 세션이나 다른
개발자가 이 코드베이스를 처음 보더라도 전체 그림을 잡을 수 있도록 자체 완결적으로
작성했다.

## 상품 목록과 가격 (2026-09-03 기준, `src/db/points.js`의 `PRICES`)

| 상품 | 가격 | LLM 호출 방식 |
|---|---|---|
| 평생사주 (`full`) | 14,900원 | 18챕터, 챕터당 1회씩 총 18회 |
| 궁합 리포트 (`compat`) | 4,900원 | 1회 (전체 본문 한 번에) |
| 빠른 리딩 (`quick`) | 990원 | 1회 (18챕터 중 1개만 재사용) |
| 이사/개업/결혼/임신·출산 (`date_select_*`) | 990원 | 1회, 주제별 전용 프롬프트 |
| 궁합운/재물운/건강운 (`life_topic_*`) | 2,900원/990원/990원 | 1회, 주제별 전용 프롬프트 |
| 오늘의 운세 (`today-fortune`) | 무료 | 0회 — LLM 미사용, 결정론적 |
| 이직 시기 / 재회 가능성 (`career_timing`/`reunion`) | 990원 | 0회 — LLM 미사용, 결정론적 |

## 1. 평생사주 — 18챕터 체계 (다른 상품들의 뿌리)

핵심 파일: `src/llm/chapters.js`(챕터 레지스트리), `src/llm/promptBuilder.js`(프롬프트
조립), `src/llm/systemPrompt.js`(공통 시스템 프롬프트), `src/llm/generateReport.js`
(18회 호출 루프), `src/reference/interpretation.md`(해석 사전).

### 챕터 레지스트리 (`chapters.js`)

18개 챕터 각각이 다음을 갖는다:
- `engineFieldPaths`: `computeSaju()` 결과 JSON 중 **이 챕터만 볼 수 있는 필드**
  (예: 4장 "십신 구조"는 `counts.shipsinGroup` 등만, 명식 전체를 다 안 넘김)
- `interpretationRefs`: `interpretation.md`에서 참고할 섹션 번호(들)
- `targetWords`: 목표 분량 (3,200~6,500자, 챕터마다 다름)

챕터 1(총평)부터 18(마무리)까지 — 성격/기질, 오행 밸런스, 십신 구조, 격국, 용신,
대운 흐름, 재물운, 직업운, 학업운, 애정·결혼운, 건강운, 대인관계, 가족운, 신살,
평생 길흉 캘린더, 개운법, 마무리 총조언 순.

### 생성 루프 (`generateReport.js`)

- 챕터 1개 = LLM 호출 1번. **3개씩 묶어(`CONCURRENCY = 3`) 동시에** 실행한다.
- "중복 서술 방지"를 위해 **이전 챕터들의 요약**(각 챕터 생성 후 `summarize()`로
  뽑은 첫 1~2문장)을 다음 챕터 프롬프트에 함께 넘긴다.
- **알려진 결함**: `priorSummaries(idx)`는 `results.slice(0, idx)`를 읽는데, 같은
  배치(3개)는 동시에 시작하므로 서로의 결과가 아직 `results` 배열에 안 채워진
  상태다. 즉 **같은 배치로 묶인 3개 챕터끼리는 서로의 요약을 못 보고 씁니다**
  (예: (1,2,3장), (4,5,6장), (7,8,9장)... 이런 3개 단위로 서로 내용이 겹칠 위험이
  더 큼). 배치 경계를 넘어간 챕터끼리만 중복 방지가 실제로 작동한다.
- 중간 실패 시 `output/<jobId>/chapters.json`에 매 챕터 완료 즉시 저장 → 이어서
  재시도 가능.

### 프롬프트 조립 (`promptBuilder.js`)

- `interpretation.md`를 `## 숫자.` 헤더 기준으로 섹션 캐싱해두고, 해당 챕터가
  참조할 섹션만 슬라이스해서 프롬프트에 넣는다(관련 없는 해석 사전까지 다 주면
  엉뚱한 근거로 서술할 위험이 있어서 방지).
- 이름이 없으면 프롬프트에 `이름: (익명)`으로 들어간다 — 이 부분은 정상 처리됨.
  (단, 이 값과 별개로 PDF 표지 템플릿 `partials/cover.ejs`는 `person.name || '평생사주'`를
  써서 "평생사주 님의 평생사주"라는 다른 결과가 나온다 — 아래 "발견한 문제" 참고.)

### 공통 시스템 프롬프트 (`systemPrompt.js`)

10가지 절대 원칙을 강제:
1. 엔진 JSON에 없는 명리학적 사실은 새로 계산·추측 금지
2. 소수점 인용 절대 금지 (개수·등급으로만)
3. null 필드는 조용히 생략(지어내지 않음)
4. JSON의 영문 필드명을 문장에 그대로 옮기지 않음
5. 순수 한국어만 (간지·한자 표기는 예외)
6. 수명·사망·불치병 확정, 임신/낙태 단정, 이혼·파산 확정, 투자종목 단정 금지
7. 부적·굿·비싼 개명 강매 금지
8. 타인 사주(궁합)는 "경향·포인트"로만, 단정 금지
9. 명리학 전문용어는 등장할 때마다 즉시 괄호로 풀이 (매 문단 반복 허용)
10. 챕터당 핵심 결론 2~5곳만 `**강조**`

톤: 2인칭 상담체 존댓말, 별점/혈액형식 일반론 금지, 반드시 실제 간지·개수·격국·
용신을 근거로 든 문장만.

## 2. 궁합 리포트 (4,900원)

핵심 파일: `src/llm/compatPromptBuilder.js`, `src/llm/generateCompatReport.js`.

- 18챕터 체계와 무관하게 **단일 프롬프트 1회 호출**로 전체 본문(2,200자, 4~5문단)을
  받는다.
- 문단 순서가 프롬프트에 고정: ①두 사람의 상호 십신(누가 누구에게 어떤 의미인지)
  → ②일지-일지 관계(배우자궁끼리 합/충) → ③나머지 교차 합충 중 1~2개만 선별
  → ④종합 점수 기반 총평.
- 같은 `systemPrompt.js`를 재사용.
- **발견한 문제**: 프롬프트 내부에 `## ${personA.name || 'A'}님의 명식`처럼
  이름이 없으면 "A"/"B"라는 글자가 그대로 들어간다. 이건 PDF 템플릿(`compat.ejs`)의
  표지에도 그대로 노출될 뿐 아니라, **LLM이 실제 본문에서 "A님은..."이라고 쓸
  가능성도 있다** — 템플릿 폴백보다 한 단계 더 심각한 전파 경로.

## 3. 빠른 리딩 (990원)

핵심 파일: `src/llm/quickReading.js`.

- 새 로직이 아니라 **18챕터 체계에서 챕터 1개만 재사용**한다.
- 주제 → 챕터 매핑: `total`=1장(총평), `wealth`=8장(재물운), `career`=9장
  (직업·적성운), `love`=11장(애정·결혼운), `relationship`=13장(대인관계).
- 목표 분량만 900자로 줄여서(`QUICK_TARGET_WORDS`), 같은 `buildChapterPrompt`·같은
  `systemPrompt.js`를 그대로 사용.
- **사소한 죽은 코드**: `QUICK_TOPICS` 각 항목에 `price: 1000`이 있는데, 실제
  과금은 `points.js`의 `quick: 990`(주제 무관 고정값)이 적용된다. 이 `price` 필드는
  어디서도 읽지 않음.

## 4. 날짜선택 4종 — 이사/개업/결혼/임신·출산 (990원)

핵심 파일: `src/server/routes/dateSelect.js`, `src/llm/dateSelectReading.js`.

- 18챕터 체계와 **완전히 별개의 자체 시스템 프롬프트**(`dateSelectReading.js` 내부,
  9개 규칙 — 취지는 `systemPrompt.js`와 같지만 별도 파일에 다시 작성됨).
- 주제별(이사/개업/결혼/임신출산) 프롬프트 빌더 함수가 각각 따로 있고, 리포트의
  소제목 순서가 고정되어 있다(예: 이사 = "언제가 좋을까" → "방향과 동네 분위기" →
  "먼저 들이면 좋은 물건").
- "구체적으로 써야 하지만 지어내면 안 되는" 요구를 **오행→색/방위/사물/맛 고정
  매핑표**로 해결한다. LLM은 이 표 안에서 고르기만 하고, 새로운 구체적 사실
  (실제 지역명, 공간 좌표 등)은 만들지 않는다.
- 이름이 없으면 서버 코드에서 `personName || '고객'`으로 정상 폴백 (문제 없음).

## 5. 궁합운/재물운/건강운 (2,900원/990원/990원)

핵심 파일: `src/server/routes/lifeTopics.js`, `src/llm/lifeTopicsReading.js`.

- 날짜선택과 같은 설계 원칙, **또 다른 별도 시스템 프롬프트**(`lifeTopicsReading.js`
  내부, 8개 규칙 — 역시 유사 내용이 세 번째로 다시 작성됨).
- 오행→자연물 비유(예: "장작과 불꽃")·색·방향·맛·운동·장부 고정 매핑표 사용.
- 궁합운은 상대방이 있으면 실제 궁합 계산(`analyzeCompatibility`)을, 솔로면 현재
  대운의 십성 그룹을 근거로 삼는다.
- 이름이 없으면 `basics.personName || '고객'`으로 정상 폴백 (문제 없음).

## 6. 오늘의 운세 (무료)

핵심 파일: `src/engine/todayFortune.js`.

- **LLM을 전혀 호출하지 않는다.** 오늘 날짜의 일진 간지가 내 일간 기준으로 어느
  십성 그룹(비겁/식상/재성/관성/인성)에 해당하는지만 계산해서, 그룹별로 미리
  써둔 고정 문구(제목/설명/DO·DON'T/3줄요약/액땜 퀘스트 등) 중 하나를 그대로
  꺼내 쓴다.
- 점수만 매일 값이 바뀌는 계산값(`relationScore` — 오늘 간지 오행이 내 용신과
  얼마나 맞는지, life-graph와 동일 로직).
- 액땜 퀘스트의 색/방향/맛은 용신 오행 기준 고정 매핑표에서 가져옴 — 이 역시
  지어내지 않는 원칙을 따름.

## 발견한 개선점 정리

1. **시스템 프롬프트가 3벌로 흩어져 있음** — `systemPrompt.js`(18챕터/궁합/빠른리딩
   공용), `dateSelectReading.js`의 자체 프롬프트, `lifeTopicsReading.js`의 자체
   프롬프트가 "전문용어 풀어쓰기", "지어내지 않기" 등 사실상 같은 규칙을 각자
   따로 써놨다. 규칙 하나를 나중에 고칠 때 세 곳을 다 고치지 않으면 상품마다
   품질이 갈리게 된다.
2. **평생사주 배치 동시 처리로 인한 챕터 간 중복 위험** — 위 "생성 루프" 항목
   참고. 3개씩 묶여 동시 생성되는 챕터끼리는 서로의 요약을 못 보고 쓴다.
3. **이름 미입력 시 처리 불일치**:
   - 정상 폴백(문제 없음): 날짜선택 4종, 궁합운/재물운/건강운 → `'고객'`
   - 문제 있음: 평생사주 표지("평생사주 님의 평생사주"), 궁합 리포트 표지·본문
     ("A"/"B" 그대로 노출, LLM 본문까지 전파 가능), 빠른 리딩 표지(앞공백), 3초
     요약카드(앞공백), 궁합 리포트 PDF 하단 서명(구분자만 남음)
   - 관련 파일: `src/pdf/templates/partials/cover.ejs`, `src/pdf/templates/compat.ejs`,
     `src/pdf/templates/quick.ejs`, `src/pdf/summaryCard.js`, `src/llm/compatPromptBuilder.js`,
     `src/pdf/renderPdf.js`(궁합 한정)
4. **죽은 코드**: `src/llm/quickReading.js`의 `QUICK_TOPICS[*].price` 필드 (실제
   미사용, 실제 가격은 `points.js`가 결정).

3·4번은 비교적 빠르게 고칠 수 있는 것들이고, 1·2번은 코드 구조를 조금 더 손봐야
하는 작업이다.
